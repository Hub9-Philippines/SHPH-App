1. Executive Summary

A comprehensive architectural and code-level audit was conducted across the Serbisyo Flutter client app. The app has achieved substantial stability: static analysis passes with 0 errors, the Supabase backend was cleanly excised in favor of the SHPH REST API, core authentication, localization (en/fil), and profile management are in place, and upstream commit 4270445 delivered in-app WebRTC calling and fixed chat sender ownership.

However, several critical blockers, payment integration mismatches, orphaned screens, and navigation glitches must be addressed before the app can be released to production:

  • Broken Digital Payments: Card and E-wallet checkouts point to nonexistent endpoints (/api/payments/stripe/*, /api/payments/maya/*). The backend uses PayMongo.
  • Silent Data Loss in Payment Methods: Adding cards writes to an unregistered DataTableStore, causing added payment methods to immediately vanish.
  • Navigation Glitch on /category: The /category route references NavBarPage(initialPage: 'Category'), which lacks 'Category' and silently falls back to Home.
  • Booking Funnel Divergence: Parallel checkout paths exist. Home uses modern live-matching, while Product Detail pages route to legacy FlutterFlow checkouts.
  • Missing 5th Tab: Web reference features a 5-tab shell (Home, Explore, Bookings, Messages, Profile); mobile lacks the Explore tab.
  • Push Notifications Stub: Background notifications lack native FCM/APNs registration and point to an obsolete domain.

3. Critical Functional Blockers (Must Fix)

3.1 Digital Payment Integration Breakdown (PayMongo Mismatch) Blocker

Files: lib/services/payment_controller.dart & lib/pages/booking_payment/booking_payment_widget.dart

Root Cause:

  1. _fetchStripeClientSecret() posts to $baseUrl/api/payments/stripe/create-intent.
  2. _fetchMayaCheckoutUrl() posts to $baseUrl/api/payments/maya/create-checkout.
  3. Neither endpoint exists in SHPH API.yaml. The backend payment suite is built on PayMongo (/api/payments/create-intent/, /api/payments/checkout-session/, /api/payments/confirm/).
  4. In processMayaPayment(), the code receives the checkout URL and immediately returns PaymentStatus.success without ever launching the payment browser or waiting for callback confirmation.

Impact: Digital payments 404 or fake success. Only Cash on Delivery functions.

3.2 Silent Data Loss in Payment Methods Blocker

Files: lib/main/payment_methods/payment_methods_model.dart & lib/backend/supabase/database/table.dart

Root Cause: When a user adds a credit card or e-wallet, the code calls PaymentMethodsTable().insert(...) which queries DataTableStore.instance. DataTableStore has zero registered datasources. All queries return empty lists.

Impact: Any payment method added by a user is silently discarded.

3.3 Navigation Silent Fallback on /category High Priority

Files: lib/router/app_router.dart (line 211) & lib/main.dart (lines 254–259)

Root Cause: app_router.dart returns NavBarPage(initialPage: 'Category'), but NavBarPage._tabs only defines 'Home', 'Bookings', 'Messages', and 'Profile'. The index lookup returns -1, defaulting to index 0 (Home).

Impact: Any category navigation deep link fails silently and sends users to Home.
